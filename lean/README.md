# Sequence Machine in Lean

Lean 4 definitions of OEIS sequences, generated from the formulas found by [Sequence Machine](https://sequencedb.net/).
Each sequence `Axxxxxx` is defined by one of its formulas, its canonical program. Each of its other formulas comes
with a `Spec`: the claim that a program equals the definition of its sequence at every index. A `Spec` has a
theorem `correct` once it is proven.

Every sequence has a page that explains its code, e.g. [A000045 in Lean](https://sequencedb.net/lean/A000045).

## How far a definition is trusted

The provenance of a sequence, `Axxxxxx.provenance`, tells how far its definition is trusted:

- **verified**: the Lean definition is proven equivalent to the name formula of the sequence (the formula in its OEIS
  name, parsed automatically) or to an independent definition, e.g. from Mathlib, and every sequence that one uses is
  verified too. A formula that the name only filters or wraps, as in "Primes of the form 2^(2^n) + 27", is not a name
  formula. Lean does not check the parsing of the name.
- **OEIS-proven**: the Lean definition is an OEIS formula that is not marked as a conjecture, and every sequence it uses
  is verified or OEIS-proven. Lean has not checked the formula.
- **conditional**: the Lean definition is an OEIS formula that is not marked as a conjecture, but it uses sequences
  whose definitions are only conditional or conjectured, so it is only correct if theirs are.
- **conjectured**: the Lean definition is a formula that matches the known terms it was checked against, but it is not
  proven.
- **undefined**: none of its formulas qualifies as a definition, so it is an opaque constant: other definitions can use
  it, but Lean knows nothing about its values.

A proof of a `Spec` only shows that the program equals the Lean definition, it is as trusted as the definition.

## Layout

- `SequenceMachineLib/`: the semantics of the operations used by the formulas, e.g. recursions and rounding.
- `Seq/`: the definitions, `def Axxxxxx (n : ℕ) : ℤ`, each given by its canonical program. The bands
  `Seq/B000`, `Seq/B001`, ... are in dependency order: a definition only uses the definitions of earlier bands or
  those before it in its file. `Seq/Opaque/` holds the undefined sequences.
- `Prog/`: the other programs of each sequence with their `Spec` and the `correct` theorems found by tactics, in files
  of 100 sequences, e.g. `Prog/A000/A0002.lean` holds A000200 to A000299.
- `Proof/`: hand-written proofs, one file per sequence, e.g. `Proof/A000/A000045.lean`: the anchor `A000045.anchor`, a
  theorem that the definition equals an independent definition, and the proofs `A000045.P<hash>.correct` of the
  claims in `Prog/`. A proof is used once it is checked to prove its statement (the `Spec`, or the statement of the
  anchor, a claim about its sequence) with no axioms but `propext`, `Classical.choice` and `Quot.sound`. The anchor
  statement must read on its own, with the file's `open` commands but without its local notation.
- `provenance.tsv`: per sequence, its provenance, the sequences a conditional definition relies on, the module of its
  definition, its canonical program, the name formula that verifies it and its programs.
- `statistics.tsv`: the number of sequences, programs and proofs by kind.

Everything except `Proof/` is generated by the Sequence Machine export, which overwrites changes to these files.

## Build

With [elan](https://github.com/leanprover/elan) installed:

```sh
lake exe cache get
lake build Seq Prog Proof
```

`lake exe cache get` downloads the built Mathlib. The whole project is several thousand modules. To build the
modules of one sequence, use the script under Reproduce on its page, which downloads only the files it needs.
